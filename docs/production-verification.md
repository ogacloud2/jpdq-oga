# 本番（業務の Databricks 環境）で検証する手順

[Databricks Free Edition の手順書](databricks-free-edition.md)で確認できたのは、**無料のサーバーレス環境で、小さなサンプルが期待どおりに動くこと**です。
業務で使う前に、次の 3 つは別に確かめる必要があります。この文書は、その手順と、合否の決め方です。

| Free Edition で確認済み | 本番で**別に確かめること** |
| --- | --- |
| サーバーレス（Spark Connect）で、ライブラリを入れて動く | 業務のクラスター・ジョブ・DBR（ランタイム）で、入れて動くか。権限・ネットワーク制限があっても動くか |
| 4 行や 3 行のサンプルで、判定が期待どおり | **実データ**で、見逃しや誤検出が許容範囲か |
| 12 万行の郵便番号表を作れる | 実際の件数で、時間・費用が許容範囲か。参照データを継続して更新できるか |

> **前提と注意**
> - この文書の手順は、**本番データを書き換えません**（読み取りと、検証用の別スキーマへの書き込みだけです）。
> - 各項目の「期待する結果」は、手元の環境と Free Edition での結果から書いています。**本番の DBR・クラスターで実際にどうなるかは、まだ確認していません。** 結果は記録し、違えば知らせてください。
> - 個人情報を含むデータを扱うときは、組織の規程に従い、結果の画面・ログに実値を残さない方法（件数と割合だけを記録する）で行ってください。

## 0. 進める前に決めること

次の 4 つを、検証を始める前に決めて、記録欄（末尾）に書いておきます。後から決めると、合否が恣意的になります。

| 決めること | 例 |
| --- | --- |
| 対象のチェックとデータ | 法人番号（取引先マスタの `corporate_number` 列）、和暦（契約日の文字列列）など |
| 検証する環境 | クラスターの種類（汎用 / ジョブ / SQL ウェアハウス / サーバーレス）、DBR のバージョン、Photon の有無 |
| 合格基準 | 「確実に誤りの値を 100% 検出」「正しい値の誤検出が 0 件」「1 億行を○分以内」など |
| 結果の使い道 | 警告（`warn`）として流す / 隔離（`error`）して後続を止める / 当面は測定だけ |

## 1. 環境の確認（動くかどうか）

### 1-1. 前提の確認

| 確認項目 | 方法 | 期待する結果 |
| --- | --- | --- |
| DBR と Spark のバージョン | ノートブックで `spark.version` を表示 | 手元で確認済みの範囲は PySpark 3.5.x。**Spark 4.x を使う DBR（17 以降）では未確認**です（このパッケージの依存は `pyspark>=3.5,<4`、`databricks-labs-dqx>=0.16,<0.17` に固定しています） |
| ANSI モード | `spark.conf.get("spark.sql.ansi.enabled")` | `true` / `false` のどちらでも動く（手元のテストは両方で通っています）。結果を記録します |
| ライブラリの取得経路 | 組織の方針を確認（PyPI への接続可否、社内ミラー、Volume からの取り込み） | `databricks-labs-dqx==0.16.0` と、`jpdq-oga` の ZIP または wheel を入れられる経路がある |
| 権限 | 検証用スキーマの作成・書き込み、元データの読み取り | 検証用スキーマ（例 `dev.jpdq_check`）に書ける。元データは **読み取りのみ**で足りる |

### 1-2. インストールとスモークテスト

1. 検証用のノートブックを、対象のクラスター（またはジョブ）に接続します。
2. [Free Edition の手順書](databricks-free-edition.md) の 5・6 と同じ方法で、`jpdq-oga-main.zip` を Volume に置き、インストールします。
   クラスターのライブラリとして入れる場合は、組織の方針に従ってください。
3. 部 A（`examples/databricks_free_edition.py` の「A.」以下）を実行します。

**期待する結果**（Free Edition と同じ）

- 「問題のない行」が 2 行（id 1・4）、違反が 8 行（id 2・3 が各 4 件）、メッセージが日本語
- 部 B で、基準日の違いにより `9999991` と `9999992` の判定が入れ替わる

**ここで失敗した場合**は、先の検証に進まず、エラー全文・DBR のバージョン・クラスター種別を記録して知らせてください。

## 2. 正しさの確認（答えが分かっているデータで）

実データに当てる前に、**正解が分かっているデータ**で判定を確かめます。ここで合格しないと、実データの結果を解釈できません。

### 2-1. 法人番号・インボイス・地方公共団体コード

1. 国税庁の[法人番号公表サイト](https://www.houjin-bangou.nta.go.jp/)で、**実在する法人番号を 20〜50 件**取得します
   （規模・設立年・所在地がばらつくように選びます）。
2. その各番号について、次の 4 種類の入力を作ります。

   | 種類 | 作り方 | 期待する判定 |
   | --- | --- | --- |
   | 正しい番号 | そのまま | 問題なし |
   | 末尾を 1 桁変える | 末尾を別の数字に | 違反（チェックディジット） |
   | 隣り合う**異なる** 2 桁を入れ替える | 例: 5 桁目と 6 桁目（同じ数字どうしは、入れ替えても同じ番号になるので除く） | 違反（ただし、`9` と `0` の入れ替えは検出できません。仕様です。この組は、期待値から除きます） |
   | 桁数を変える | 12 桁・14 桁 | 違反（形式） |

3. 結果が期待と違う行が **1 件でもあれば不合格**です（チェックディジットは確定的な計算なので、例外は想定していません）。
4. 地方公共団体コードは、次の値で確認します。

   | 入力 | 期待する判定 |
   | --- | --- |
   | `162019`（総務省の算出例） | 問題なし |
   | `162010`（検査数字が不一致） | 違反 |
   | `480008`（先頭 2 桁が 47 を超える） | 違反 |

### 2-2. 和暦

次の表の入力で、判定を確認します。

| 入力 | 期待する判定 |
| --- | --- |
| `令和元年4月30日` | 違反（令和は 5 月 1 日から） |
| `令和元年5月1日` | 問題なし |
| `平成31年5月1日` | 違反（すでに令和元年） |
| `平成31年4月30日` | 問題なし |
| `令和6年2月30日` | 違反（存在しない日付） |
| `昭和57年2月29日` | 違反（平年） |
| `令和2年2月29日` | 問題なし（閏年） |
| `明治5年12月31日` | 違反（旧暦。`pre_gregorian`） |

### 2-3. 参照データ（郵便番号・地方公共団体コード）

1. 日本郵便の最新の `utf_ken_all.zip`、総務省の Excel 2 つを、Free Edition の手順書（8 章）と同じ方法で取り込み、**検証用スキーマに**表を作ります。
2. 次を確認します。

   | 確認 | 期待する結果 |
   | --- | --- |
   | 行数 | 郵便番号表: 約 12 万行（Free Edition での結果は 120,877 行。データ更新で少し変わります） |
   | 注記 | 総務省の表: `current code list as of 2024-01-01; revisions from 2005-04-01` のような表示 |
   | 既知の廃止 | 浜松市の旧 7 区（`221317` ほか）が `valid_to = 2024-01-01`、那珂川町（福岡）`403059` が 2018-10-01 |
   | 存在しない値 | `000-0000` が「存在しない」、東京の郵便番号と `大阪府` の組み合わせが「不一致」 |

## 3. 実データでの確認（読み取りだけ、サンプルから）

### 3-1. サンプルを取り出す

本番の表を直接書き換えず、**読み取って検証用スキーマに複製**します。最初は小さく始めます。

```python
SRC = "prod.sales.customers"            # 元の表（読み取りのみ）
DST = "dev.jpdq_check.customers_sample"  # 検証用スキーマの複製先

spark.table(SRC).sample(fraction=0.01, seed=42).limit(1_000_000).write.mode("overwrite").saveAsTable(DST)
print(spark.table(DST).count(), "行")
```

> 元の表に書き込む操作は、この手順にはありません。権限は読み取りだけで足ります。

### 3-2. チェックを当てて、違反の内訳を見る

```python
import yaml
from databricks.labs.dqx.engine import DQEngine
from databricks.sdk import WorkspaceClient
from pyspark.sql import functions as F
from jpdq_oga import get_japan_checks

checks = yaml.safe_load("""
- name: corporate_number
  criticality: warn
  check:
    function: is_valid_jp_corporate_number
    arguments: {column: corporate_number}
""")

df = spark.table("dev.jpdq_check.customers_sample")
engine = DQEngine(WorkspaceClient())
out = engine.apply_checks_by_metadata(df, checks, custom_check_functions=get_japan_checks())

total = out.count()
violations = out.filter(F.col("_warnings").isNotNull()).count()
print(f"対象 {total} 行、違反 {violations} 行（{violations / total:.2%}）")
```

> `criticality: warn` の場合は `_warnings` 列、`error` の場合は `_errors` 列に入ります。違反が無いとき、列は空配列ではなく `NULL` です。

### 3-3. 違反を人の目で確認する（誤検出の見積もり）

1. 違反行のうち、**50〜100 件を無作為に選び**、1 件ずつ原因を分類します（個人情報を扱う場合は、実値を記録せず、分類だけを記録します）。

   | 分類 | 意味 | 対応 |
   | --- | --- | --- |
   | 真の誤り | 入力ミスなど、直すべき値 | チェックは正しく動いている |
   | 仕様による誤検出 | 下の「想定される誤検出」に当てはまる | 対象から除くか、別の扱いにする |
   | 想定外 | 上のどれでもない | **不具合の可能性。知らせてください** |

2. 想定外が **1 件でもあれば、原因を調べてから**先に進みます。

**想定される誤検出（README の「仕様と制限」より）**

- インボイス登録番号は**法人形式のみ**が対象です。個人事業者の番号（`T` + 13 桁）は、正しくても違反になりえます。
- 郵便番号の実在性は**町域の郵便番号のみ**が対象です。大口事業所の個別番号は「存在しない」になります。
- 都道府県・市区町村は、日本郵便データの表記どおりでないと不一致になります（表記ゆれ）。
- 全角数字・前後の空白・小文字の `t` は、直さずに形式違反として報告されます。

### 3-4. 見逃しの見積もり（誤りなのに通った値）

このチェックが検出できないものがあります。次を理解したうえで、業務上の許容範囲かを確認します。

- 法人番号: **形式とチェックディジットだけ**で、実在確認はしません。`9` と `0` の隣り合う入れ替えも通ります。
- `NULL` は違反になりません。必須項目は DQX の `is_not_null` と組み合わせます。

## 4. 規模と性能の確認

1. 検証用に、**実際の本番に近い件数**の表を用意します（例: 本番の 1 日分、または全件の複製を検証用スキーマに作る）。
2. 同じ表で、**チェックを付けない処理**と**付けた処理**の時間を測ります（同じクラスター・同じ条件で、3 回以上）。

   | 測るもの | 記録 |
   | --- | --- |
   | 処理時間（チェックなし / あり） | 中央値、最小・最大 |
   | クラスター | ノード種別と台数、DBR、Photon の有無 |
   | 参考値 | GitHub Actions（2 vCPU）で 1,000 万行の法人番号が 6.9 秒、和暦が 37.7 秒（[BENCHMARK.md](../BENCHMARK.md)）。**Photon・クラスターでの計測はしていません** |

3. 合格基準（手順 0 で決めた値）に収まるかを確認します。DQX は、行ルールの条件列を複数回評価するため、式の単体評価より遅くなります。

## 5. 運用の確認（継続して使えるか）

| 確認項目 | 方法 | 期待する結果 |
| --- | --- | --- |
| 参照データの更新 | `cli.build_postal(spark, zip, 作業フォルダ, "utf-8", spark.table(既存の表), 取得日)` で、翌月分を既存の表に重ねる（CLI なら `--existing-table`）。重ねた結果は、**別の表**に書いて確認してから置き換えます | 履歴が残り、古い基準日（`as_of`）でも結果が再現できる |
| 基準日の指定 | 固定日（`as_of`）と、行ごとの日付（`as_of_column`）の両方 | どちらでも期待どおりの判定になる |
| 権限 | 検証用スキーマと、本番の参照表を読む人・書く人 | 参照表は書き込める人を限定している。読む人は、チェックを実行する人 |
| ジョブ化 | ジョブ（ワークフロー）として実行し、失敗時の通知を確認 | 実行ログに、違反件数だけが出る（実値が出ない） |
| 取得の失敗 | 日本郵便の取得が失敗したときの手順 | 手作業の取り込み手順が、運用手順書にある（自動取得は、ブラウザ以外を断られる可能性があります） |
| 戻し方 | チェックを外す、または `warn` に戻す方法 | 1 つの設定変更で、後続への影響を止められる |

## 7. 適用の進め方（推奨）

1. **測定だけ**（違反を数えて記録し、後続に影響させない）から始めます。
2. 結果が落ち着いたら、`criticality: warn` で適用します（通知・隔離はしない）。
3. 誤検出が許容範囲と確認できたものだけ、`criticality: error` にします。

何か動かなかった場合は、**どの手順か、DBR のバージョン、エラー全文**を知らせてください。
